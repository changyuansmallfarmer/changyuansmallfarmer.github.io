linux如何理解“平均负载”

一、问题引入：为什么系统卡了，CPU 却不高？​

某天凌晨，监控告警：“服务器 load average 突增至 20！” 你赶紧登录服务器：

$ uptime
 12:30:01 up 30 days,  5:22,  2 users,  load average: 20.12, 18.45, 15.67

再看 top：

%Cpu(s):  2.1%us,  0.5%sy,  0.0%ni, 97.0%id,  0.3%wa,  0.0%hi,  0.1%si,  0.0%st

CPU 空闲率高达 97%！那为什么 load 这么高？系统还卡得打不开网页？

——这正是很多新手的困惑：“load 高 ≠ CPU 高”。

今天，我们就彻底搞懂 Linux 平均负载（Load Average） 到底是什么、怎么查、如何分析。

二、什么是“平均负载”？​

官方定义（简化版）：​

平均负载 = 系统中处于“可运行状态” + “不可中断睡眠状态”的平均进程数

注意！它不是 CPU 使用率，而是对系统整体“繁忙程度”的度量。

拆解两个关键状态：​

状态说明常见场景
可运行（Runnable）正在使用 CPU 或等待 CPU 调度CPU 密集型任务（如计算、编译）
不可中断睡眠（Uninterruptible Sleep, D 状态）进程在等待 I/O（磁盘、网络等），且不能被信号中断磁盘慢、NFS 卡住、硬件故障

💡 关键点：即使 CPU 很空，只要大量进程卡在 I/O（比如磁盘响应慢），load 也会飙升！

三、三个数字代表什么？​

load average: 1.20, 0.95, 0.78

这三个数分别是：

  • 1分钟平均负载
  • 5分钟平均负载
  • 15分钟平均负载

它们是指数加权移动平均（EWMA），越近的数据权重越高。

如何判断是否“过高”​

经验法则： Load < CPU 核心数 → 系统健康 Load ≈ CPU 核心数 → 系统满载但可控 Load > CPU 核心数 × 2 → 可能存在性能瓶颈，需排查！

例如：4 核服务器，load 持续 > 8，就该警惕了。

⚠️ 注意：不是绝对值越低越好！偶尔 spike 是正常的。

四、实战：如何定位高负载原因？​

步骤 1：确认 load 是否真的高​

$ uptime
$ cat /proc/loadavg

步骤 2：查看哪些进程在“作怪​

# 查看所有处于 D 状态（不可中断睡眠）的进程
$ ps aux | awk '$8 ~ /^D/ \{print $0\}'

输出示例：

root      1234  0.0  0.0      0     0 ?        D    10:00   0:05 [kworker/2:1]
user      5678  0.0  0.1 123456 7890 ?        D    10:05   0:02 ./my_app

如果看到大量 D 状态进程，基本可以确定是 I/O 问题（磁盘、存储、NFS 等）。

步骤3 ：检查 CPU 和 I/O 使用情况​

# 实时监控 CPU、内存、I/O
$ top          # 按 '1' 看各核负载
$ iostat -x 2  # 查看磁盘 util%、await
$ dstat        # 综合监控（推荐）

重点关注：

  • iostat 中的 %util > 90%？→ 磁盘饱和
  • await（I/O 平均等待时间）> 20ms？→ 磁盘慢

步骤 4：深入分析（高级）​

# 查看具体进程的 I/O
$ pidstat -d 2

# 查看内核线程（如 kswapd、jbd2）是否活跃
$ top -p $(pgrep -d',' kswapd)

# 检查是否有大量僵尸进程（虽不影响 load，但需清理）
$ ps aux | grep 'Z'

五、内核计算机制：指数加权移动平均法（EMA）​

5.1 为什么不是简单平均？​

内核不使用"过去1分钟内的平均进程数"，因为那需要保存60个采样点。内核采用EMA算法，特点：

  1. 计算高效：仅需保存上一个值，O(1)复杂度
  2. 趋势敏感：越近的数据权重越大，能更快反映系统变化

5.2 核心算法实现​

内核源码位置：kernel/sched/core.c

// 指数加权移动平均计算
static unsigned long calc_load(unsigned long load, unsigned long exp, unsigned long active)
\{
    load *= exp;                    // 历史值衰减
    load += active * (FIXED_1 - exp); // 加入当前活跃进程数
    load += 1UL << (FSHIFT - 1);    // 四舍五入
    return load >> FSHIFT;          // 右移还原
\}

// 每5秒调用一次
void calc_global_load(void)
\{
    long active = atomic_long_read(&calc_load_tasks); // 当前活跃进程数
    
    // 计算1/5/15分钟负载
    avenrun[0] = calc_load(avenrun[0], EXP_1, active);
    avenrun[1] = calc_load(avenrun[1], EXP_5, active);
    avenrun[2] = calc_load(avenrun[2], EXP_15, active);
\}

关键参数：

  • active：当前瞬间的R + D进程总数
  • EXP_1/5/15：指数衰减系数，分别对应1/5/15分钟的时间常数
  • avenrun[]：全局数组，保存三个时间段负载值

六、常见高负载场景与解决方案​

场景表现解决方案
磁盘性能瓶颈load 高，CPU idle 高，iostat %util=100%升级 SSD、优化数据库查询、加缓存
NFS/GlusterFS 卡住大量 D 状态进程，挂载点无响应检查网络、服务端负载、超时设置
内存不足 + 频繁 swapkswapd 占用高，load 飙升增加内存、减少应用内存占用
CPU 密集型任务堆积load 高，CPU us/sy 高限流、扩容、优化算法
内核 bug 或硬件故障随机 D 状态、无法 kill升级内核、检查 RAID/SMART

七、总结​

  • Load Average ≠ CPU 使用率
  • 高 load 可能由 CPU 繁忙 或 I/O 阻塞 引起
  • D 状态进程是 I/O 问题的关键线索
  • 排查思路：uptime → ps aux → iostat/dstat → pidstat
  • 核心：不要孤立看指标，要关联分析，必须结合上下文**：CPU、内存、磁盘、网络、业务日志。**
