系统中出现大量不可中断进程和僵尸进程如何排查

前言：进程状态里的 “异常信号”​

作为 Linux 开发，ps 和 top 是日常排查问题的 “老朋友”。通过它们，我们能快速看到进程的运行状态 —— 运行（R）、空闲（I）、可中断睡眠（S）、暂停（T）这些状态大多无需过度关注，但不可中断睡眠（D） 和 僵尸（Z） 两种状态，往往是系统隐患的 “信号灯”。

今天我们就从基础认知出发，结合实际排查场景，聊聊如何用 ps/top 初步定位，再用 dstat/pidstat/perf/pstree 等工具深挖根源，最终解决这两类进程引发的系统问题。

一、先厘清：D 状态和 Z 状态到底是什么？​

在动手排查前，必须先明确两个状态的核心定义，避免踩坑：

1. 不可中断睡眠（D 状态）：“正在跟硬件打交道，别打扰我”​

  • 本质：进程正在执行与硬件相关的操作（如磁盘读写、网络 I/O、设备驱动交互），为了保证数据一致性（比如避免磁盘写一半被中断导致文件损坏），系统会禁止任何进程或中断打断它。

  • 关键特征：ps/top 中状态显示为 D，无法用 kill -9 强制终止（强行 kill 只会白费功夫）。

  • 正常 vs 异常：短暂的 D 状态是正常的（比如拷贝大文件时，进程会短暂处于 D 状态等待磁盘 I/O）；但大量 D 进程持续存在（超过几分钟），通常意味着系统存在 I/O 性能问题（如磁盘瓶颈、挂载点卡死）。

2. 僵尸状态（Z 状态）：“进程已死，资源未回收”​

  • 本质：进程已经执行完退出（exit），但它的父进程没有调用 wait() 或 waitpid() 函数，回收它占用的 PID、进程表项等资源，导致它成为 “僵尸”。

  • 关键特征：ps/top 中状态显示为 Z，不占用 CPU 和内存，但会占用有限的 PID 资源。

  • 正常 vs 异常：短暂的 Z 状态无需理会（父进程可能延迟回收）；但大量 Z 进程堆积，会导致系统无法创建新进程（PID 耗尽），此时必须排查父进程问题。

补充：关于 iowait 高的 “误区”​

很多人会把 top 中看到的高 iowait（I/O 等待时间占比）直接等同于 “磁盘 I/O 瓶颈”，但这是不准确的：

  • 当系统中只有 I/O 类型的进程在运行时（比如没有其他 CPU 密集型进程），iowait 数值会被 “放大”，但实际磁盘读写可能远未达到性能上限。

  • 正确逻辑：iowait 升高 → 先用工具验证是否真的是 I/O 问题 → 再定位对应进程，而不是直接判定磁盘故障。

二、排查流程：从 “初步定位” 到 “根源深挖”​

第一步：用 ps/top 快速识别异常进程​

这是排查的起点，先确认系统中是否存在大量 D/Z 状态进程：

# 1. 用 ps 列出所有 D/Z 状态进程（含 PID、PPID、命令）
ps aux | awk '$8 ~ /D|Z/ \{print "PID:"$2, "PPID:"$3, "状态:"$8, "命令:"$11\}'

# 2. 用 top 实时观察（按「状态」排序，重点看 D/Z 列）
top -o S  # 按状态字段排序，D/Z 进程会集中显示

通过这两个命令，你能快速得到：

  • 异常进程的 PID 和父进程 PPID；

  • 对应的执行命令（比如是数据库进程、NFS 挂载进程还是自定义应用）；

  • 异常进程的数量（判断是个别问题还是批量异常）。

第二步：处理 D 状态进程：先验证 I/O，再找根源​

大量 D 进程的核心怀疑对象是 “I/O 阻塞”，但需先通过工具验证，再针对性排查：

1. 验证是否真的是 I/O 问题（破除 iowait 误区）​

用 dstat 和 pidstat 工具确认 I/O 负载（若未安装，需先执行 yum install dstat sysstat）：

# 1. dstat 实时查看磁盘 I/O 状态（重点看 read/write 速度和 %util 利用率）
dstat -d -D sda,sdb  # 只显示 sda、sdb 磁盘的读写状态
# 输出示例：read 100M/s, write 50M/s, %util 95% → 接近饱和，确认为 I/O 瓶颈

# 2. pidstat 定位哪个进程导致 I/O 压力
pidstat -d 1  # 每秒输出一次进程 I/O 统计
# 重点看 %dio（磁盘 I/O 占比），数值高的进程即为元凶

若 dstat 显示磁盘 %util 远低于 100%，但 iowait 仍很高 → 说明是 “伪 I/O 瓶颈”（系统无其他进程运行），无需优化磁盘，只需关注 D 进程本身的 I/O 等待原因（如网络 I/O 阻塞）。

2. 深挖 D 进程的阻塞原因​

根据第一步的验证结果，分场景排查：

  • 场景 1：磁盘 I/O 阻塞（% util 接近 100%）

  • 检查磁盘健康状态：smartctl -a /dev/sda（查看磁盘坏道、寿命）；

  • 检查挂载点是否卡死：df -h（若命令卡住，大概率是 NFS/GlusterFS 等网络挂载失效）；

  • 解决：强制卸载失效挂载点 umount -lf /mnt/nfs，更换挂载源；或更换故障磁盘。

  • 场景 2：网络 I/O 阻塞（磁盘 % util 正常）

  • 查看 D 进程的网络连接：netstat -anp | grep 进程PID；

  • 若连接状态为 SYN_SENT/ESTABLISHED 但长期无数据传输 → 说明进程在等待远程服务响应（如数据库、API）；

  • 解决：检查远程服务可用性（ping/telnet），或在应用中添加网络超时配置（避免无限等待）。

  • 场景 3：直接 I/O 导致的特殊情况

若上述排查均无结果，且 D 进程后续变成 Z 进程（无法用 strace 跟踪系统调用），需用 perf 工具分析 CPU 时钟事件，定位内核 / 应用层面的问题：

# 1. 安装 perf：yum install perf
# 2. 跟踪系统级 CPU 事件（持续 30 秒）
perf record -g -a sleep 30
# 3. 查看分析结果（按热点排序）
perf report

实战中，我们曾通过 perf 发现：某应用使用直接 I/O（O_DIRECT 标志）读写文件时，未正确处理 I/O 完成事件，导致进程长期处于 D 状态，后续退出后变成 Z 进程。通过修复源码中直接 I/O 的处理逻辑，问题彻底解决。

第三步：处理 Z 状态进程：找到父进程，就是找到根源​

僵尸进程的排查相对直接，核心是 “定位父进程”—— 因为僵尸进程的资源回收责任在父进程：

1. 用 pstree 找到僵尸进程的父进程​
# 1. 先获取僵尸进程的 PID（从第一步 ps 命令结果中提取）
# 2. 用 pstree 查看父进程链（-p 显示 PID）
pstree -p | grep 僵尸进程PID
# 示例输出：systemd(1)───nginx(1234)───nginx(5678)───nginx(7890)Z
# 其中 1234 是 7890（僵尸进程）的父进程 PPID
2. 排查父进程的问题​

僵尸进程的本质是父进程未处理子进程退出，常见原因有两种：

  • 父进程程序 bug：未注册 SIGCHLD 信号处理函数，或未调用 wait()/waitpid() 回收子进程；

  • 父进程异常退出：父进程崩溃后，子进程被 init 进程（PID=1）接管，但 init 仅定期回收，若批量产生则会堆积。

3. 解决方法​

  • 应急处理：若父进程正常运行 → 重启父进程（systemctl restart 父进程服务名），重启后父进程会自动回收僵尸进程；若父进程已退出（PPID=1）→ 执行 systemctl daemon-reload 或重启系统。

  • 彻底根治：检查父进程代码：

  • 若为 C/C++ 程序：添加 SIGCHLD 信号处理函数，调用 waitpid(-1, NULL, WNOHANG) 非阻塞回收所有子进程；

  • 若为 Python/Java 程序：确保子进程退出后有对应的回收逻辑（如 Python 的 subprocess.Popen 调用 communicate()）。

三、实战总结：关键步骤与避坑指南​

1. 排查关键步骤​

2. 避坑指南​

  • ❌ 不要直接 kill -9 D 状态进程：无效！必须先解决 I/O 阻塞问题，进程才会自动退出；

  • ❌ 不要被高 iowait 误导：先用量化工具（dstat/pidstat）验证，再下结论；

  • ❌ 不要只删除僵尸进程：不修复父进程，会持续产生新的僵尸进程；

  • ❌ 不要忽略 D 转 Z 的情况：无法用 strace 跟踪时，记得用 perf 工具分析内核 / 应用热点。

四、预防措施：提前规避问题​

  1. 监控告警：用 Prometheus+Grafana 监控 node_processes_state{state=~"D|Z"}，当数量超过阈值（如 5 个）时触发告警；

  2. 应用优化：所有后台服务必须实现子进程回收逻辑，配置合理的 I/O/ 网络超时；

  3. 系统配置：定期检查磁盘健康（smartctl）、清理无效挂载点，开启内核参数 echo 30 > /proc/sys/kernel/hung_task_timeout_secs（30 秒超时清理 D 进程）。

五、典型实战案例：还原真实排查场景​

理论结合实践才能真正掌握排查思路，以下两个案例均来自生产环境，覆盖 D 转 Z 特殊场景和大规模僵尸进程问题：

案例 1：直接 I/O 导致的 D 转 Z 进程堆积​

现象：某电商平台后台服务器（CentOS 7）负载飙升至 20+，ps 查看发现 10+ 进程处于 D 状态，半小时后部分转为 Z 状态，应用日志无报错。

排查过程：

  1. 初步定位：ps aux | awk '$8 ~ /D|Z/' 发现异常进程均为自定义数据同步服务（data-sync），PPID 均为 1234（服务主进程）。

  2. 验证 I/O：dstat -d 显示磁盘 % util 仅 15%，pidstat -d 1 显示 data-sync 进程的 % dio 为 0 → 排除磁盘 I/O 瓶颈。

  3. 网络排查：netstat -anp | grep 1234 无异常网络连接，ping 数据库 / 缓存服务均正常 → 排除网络阻塞。

  4. 深度分析：使用 perf 跟踪系统事件：

perf record -g -p 1234 sleep 60  # 仅跟踪服务主进程
perf report  # 查看热点函数

发现 data-sync 进程频繁调用 pread64() 函数（直接 I/O 读写），且内核态函数 __direct_io_complete() 存在阻塞。

  1. 源码排查：查看 data-sync 源码，发现使用 O_DIRECT 标志打开文件后，未通过 aio_wait() 等待 I/O 完成，直接退出子进程，导致子进程长期处于 D 状态，最终转为 Z 状态。

解决方案：

  • 修复源码：在直接 I/O 操作后添加 aio_wait() 等待逻辑，确保 I/O 完成后再退出子进程；

  • 补充子进程回收：在主进程中注册 SIGCHLD 信号处理函数，调用 waitpid() 回收异常退出的子进程；

  • 重启服务：systemctl restart data-sync，僵尸进程被自动回收，D 进程不再产生。

案例 2：Python 服务未回收子进程导致大规模 Z 进程​

现象：某监控平台（Python 编写）运行 3 天后，服务器出现 “无法创建新进程” 报错，ps aux | grep Z 显示 200+ 僵尸进程，PPID 均为 5678（监控服务主进程）。

排查过程：

  1. 定位父进程：pstree -p 5678 发现主进程通过 subprocess.Popen 启动大量子进程（执行脚本采集数据），但未调用 communicate() 或 wait() 回收。

  2. 代码分析：查看监控服务源码，发现以下问题代码：

# 错误示例：启动子进程后未回收
for task in task_list:
    subprocess.Popen(["python", "collector.py", task])

子进程执行完毕后退出，但父进程未处理，导致僵尸进程堆积。

解决方案：

  • 紧急处理：systemctl restart monitor-service，200+ 僵尸进程瞬间被回收；

  • 代码修复：两种方案任选：

  1. 调用 communicate() 阻塞回收：
for task in task_list:
    p = subprocess.Popen(["python", "collector.py", task])
    p.communicate()  # 等待子进程退出并回收
  1. 使用 subprocess.check_output() 简化逻辑（自动回收）：
for task in task_list:
    subprocess.check_output(["python", "collector.py", task])
  • 长期优化：引入进程池（multiprocessing.Pool）限制并发数，避免子进程泛滥。

六、工具进阶用法：让排查更高效​

前面提到的工具（ps/top/perf 等）还有更多实用参数，掌握这些能大幅提升排查效率：

1. ps 进阶：精准过滤异常进程​

# 1. 显示 D/Z 进程的完整命令行（避免命令被截断）
ps auxww | awk '$8 ~ /D|Z/ \{print $2, $8, $0\}'

# 2. 统计每个父进程下的僵尸进程数量
ps -ef | grep -v grep | awk '$8 == "Z" \{print $3\}' | sort | uniq -c | sort -nr

# 3. 查看 D 进程的等待资源（需安装 pstack）
pstack 进程PID  # 若输出无响应，说明进程确实在等待硬件资源

2. top 进阶：聚焦关键指标​

# 1. 只显示 D/Z 状态进程（实时刷新）
top -p $(ps aux | awk '$8 ~ /D|Z/ \{print $2\}' | tr '\n' ',')

# 2. 显示进程的 I/O 统计（需开启）
top -o %IO  # 按 I/O 占比排序，快速找到 I/O 密集型进程
# 注：部分系统需先执行 `echo 1 > /proc/sys/kernel/threads-max` 开启

# 3. 查看每个 CPU 的 iowait 分布
top -1  # 按 1 切换到单个 CPU 视图，判断是否某颗 CPU 被 I/O 阻塞

3. perf 进阶：精准定位问题函数​

# 1. 只跟踪 I/O 相关的系统调用
perf record -e syscalls:sys_enter_pread64 -e syscalls:sys_enter_pwrite64 -p 进程PID

# 2. 生成火焰图（更直观展示调用链）
# 安装火焰图工具：git clone https://github.com/brendangregg/FlameGraph.git
perf record -g -p 进程PID sleep 30
perf script > perf.data
./FlameGraph/stackcollapse-perf.pl perf.data > perf.folded
./FlameGraph/flamegraph.pl perf.folded > perf.svg

打开 perf.svg 可直观看到进程调用链中阻塞的函数（火焰图中 “平顶” 部分即为热点）。

4. pstree 进阶：快速定位父进程树​

# 1. 以树形结构显示僵尸进程的完整父进程链（含命令）
pstree -p -a | grep -B 3 -A 3 Z  # 显示僵尸进程上下 3 层的进程链

# 2. 查找所有僵尸进程的父进程，并显示父进程的启动命令
for zpid in $(ps aux | awk '$8 == "Z" \{print $2\}'); do
    ppid=$(ps -ef | grep $zpid | awk '\{print $3\}')
    echo "僵尸进程 $zpid 的父进程 $ppid：$(ps -ef | grep $ppid | awk '\{print $0\}')"
done

七、常见场景扩展：不同环境下的特殊处理​

1. Kubernetes 环境中的 D/Z 进程​

  • 排查差异：需先进入容器（kubectl exec -it 容器名 -- /bin/bash）再执行 ps/top，或直接在节点上执行 ps aux | grep 容器ID（容器进程在节点上可见）。

  • 特殊问题：

  • D 进程：可能是容器挂载的 PVC（存储卷）故障，通过 kubectl describe pvc PVC名 查看存储状态；

  • Z 进程：若容器重启后仍存在，可能是 Pod 配置的 restartPolicy: Always 导致父进程反复重启，未回收子进程。

  • 解决方案：

  • 重建故障 PVC 或更换存储类；

  • 在容器启动脚本中添加子进程回收逻辑（如 trap 'wait' SIGCHLD）。

2. 虚拟机 / 云服务器中的 D 进程​

  • 常见原因：云盘（如 AWS EBS、阿里云 ECS 云盘）性能瓶颈或挂载点异常。

  • 特殊排查：

  • 查看云盘监控：登录云平台控制台，查看云盘的 I/O 吞吐量、延迟是否超标；

  • 检查云盘挂载：mount | grep cloud 查看挂载参数，若使用 defaults,noatime 仍卡顿，可尝试调整 io_scheduler：

echo mq-deadline > /sys/block/vda/queue/scheduler  # 切换 I/O 调度器

3. 嵌入式 Linux 中的 Z 进程​

  • 限制条件：嵌入式系统资源有限（PID 数量少，通常为 4096），僵尸进程堆积会更快导致系统崩溃。

  • 解决方案：

  • 开启内核自动回收：echo 1 > /proc/sys/kernel/auto_reap_orphans（部分嵌入式内核支持）；

  • 简化应用设计：避免频繁创建子进程，或使用线程替代子进程（线程退出后资源自动回收）。

八、总结：排查思路的核心逻辑​

解决 Linux 系统的 D/Z 进程问题，核心是 “先定位现象→再验证原因→最后根治问题”，避免盲目操作：

  1. 用 ps/top 快速锁定异常进程，获取 PID/PPID 和关联命令；
  2. 对 D 进程：先通过 dstat/pidstat 验证 I/O 是否真瓶颈，再分磁盘 / 网络 / 直接 I/O 场景排查；
  3. 对 Z 进程：核心是找到父进程，修复 wait()/SIGCHLD 处理逻辑，而非单纯删除僵尸进程；
  4. 复杂场景：善用 perf 工具和火焰图，从内核 / 应用层面深挖根源；
  5. 长期保障：通过监控告警和代码规范，提前规避问题复发。
