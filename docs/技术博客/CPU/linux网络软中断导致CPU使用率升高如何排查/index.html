linux网络软中断导致CPU使用率升高如何排查

一、实战：网络类软中断 CPU 升高的排查流程​

在生产环境中，软中断 CPU 使用率（si）升高 90% 以上是网络类软中断导致，尤其是NET_RX_SOFTIRQ（网络接收）—— 毕竟高流量服务器（如 Web、数据库、缓存）的网卡每秒可能接收数百万数据包，极易引发软中断风暴。以下是一套完整的排查闭环，结合sar、tcpdump、ethtool等工具，从定位到解决一步到位。

1. 第一步：确认是否为网络类软中断问题​

首先通过前文提到的工具，锁定问题核心：

  • 用top确认 si 占比：执行top后按1，若si列数值超过 30%（如si: 45.2%），且持续居高不下，说明软中断占用大量 CPU；

  • 用/proc/softirqs定位软中断类型：执行watch -n 1 cat /proc/softirqs（每秒刷新一次），观察哪类软中断增长最快：

  • 若NET_RX数值飞速上涨（如每秒增长数万），则是网络接收软中断问题；

  • 若NET_TX增长快，则是网络发送软中断问题（相对少见，多为大量数据并发发送场景）；

  • 用mpstat确认 CPU 负载分布：执行mpstat -P ALL 1（每秒输出所有 CPU 负载），若某几个 CPU 的si占比特别高（如 CPU0 的 si=60%），说明网络软中断集中在这些 CPU 上，可能是中断亲和性配置不当。

示例输出（mpstat）：

Linux 5.15.0-78-generic (server-01)      0/2024    86_64_    CPU)

10:00:00 AM  CPU    %usr   %nice    %sys %iowait    %irq   %soft  %steal  %guest  %gnice   %idle
10:00:01 AM  all    5.20    0.00    3.10    0.00    0.00   42.50    0.00    0.00    0.00   49.20
10:00:01 AM    0    2.00    0.00    2.00    0.00    0.00   58.00    0.00    0.00    0.00   38.00  # CPU0软中断占比58%
10:00:01 AM    1    6.00    0.00    3.00    0.00    0.00   45.00    0.00    0.00    0.00   46.00  # CPU1软中断占比45%     (8     _x   09/2

2. 第二步：用sar分析网络流量是否异常​

确认是网络类软中断后，需判断是正常高流量还是异常流量（如攻击、不合理请求）：

  • 安装 sar 工具（若未安装）：yum install sysstat（CentOS）或apt install sysstat（Ubuntu）；

  • 查看网络收发统计：执行sar -n DEV 1 10（每秒输出 1 次，共 10 次，统计所有网卡流量）：

  • 核心指标说明：

  • rxpck/s：每秒接收的数据包数；

  • txpck/s：每秒发送的数据包数；

  • rxkB/s：每秒接收的字节数（KB）；

  • txkB/s：每秒发送的字节数（KB）；

  • 异常判断标准：

  • 若rxpck/s超过 10 万（普通服务器阈值），且持续几分钟，可能是异常流量；

  • 若rxpck/s很高，但rxkB/s很低（如 rxpck/s=20 万，rxkB/s=100），说明是大量小包（如 TCP SYN Flood 攻击）。

示例输出（sar -n DEV）：

Linux 5.15.0-78-generic (server-01)   9/20/2024     6_64_  8 CPU)

10:05:00 AM     IFACE   rxpck/s   txpck/s    rxkB/s    txkB/s   rxcmp/s   txcmp/s  rxmcst/s   %ifutil
10:05:01 AM      eth0  185623.00   2345.00    987.00    123.00      0.00      0.00      0.00      0.05
10:05:02 AM      eth0  192345.00   2189.00   1023.00    118.00      0.00      0.00      0.00      0.06      (    _x8      0

注：上述示例中rxpck/s达 18 万 +，rxkB/s仅 1000 左右，属于典型的 “小包风暴”，大概率是异常流量。

3. 第三步：用tcpdump抓包分析流量类型​

若sar发现异常流量，需通过tcpdump抓包定位具体是哪种请求导致：

  • 抓包基础命令（针对 eth0 网卡，保存到文件）：
tcpdump -i eth0 -w softirq.pcap -c 10000  # 抓1万个包，保存到softirq.pcap

  • 过滤关键流量（按需调整过滤条件）：

  • 抓 TCP SYN 包（判断是否有 SYN Flood 攻击）：tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'；

  • 抓特定端口流量（如 80 端口 HTTP）：tcpdump -i eth0 port 80；

  • 抓 UDP 包（判断是否有 UDP Flood）：tcpdump -i eth0 udp；

  • 分析抓包文件（可下载到本地用 Wireshark 打开，或直接在服务器分析）：

  • 若大量 SYN 包来自不同 IP，且无后续 ACK 包，大概率是 SYN Flood 攻击；

  • 若大量重复的 HTTP 请求（如频繁请求同一接口），可能是应用层不合理调用（如客户端重试机制异常）。

示例：抓包发现 SYN Flood 攻击：

tcpdump: verbose output suppressed, use -v[v]... for full protocol decode
listening on eth0, link-type EN10MB (Ethernet), snapshot length 262144 bytes
10:10:00.123456 IP 192.168.1.100.54321 > 10.0.0.1.80: Flags [S], seq 123456789, win 65535, length 0
10:10:00.123467 IP 192.168.1.101.54322 > 10.0.0.1.80: Flags [S], seq 987654321, win 65535, length 0
10:10:00.123478 IP 192.168.1.102.54323 > 10.0.0.1.80: Flags [S], seq 456789123, win 65535, length 0
# 大量不同IP发送SYN包，无ACK响应

4. 第四步：用ethtool检查网卡配置是否合理​

除了流量问题，网卡自身配置不当也可能导致软中断升高（如网卡队列数过少、中断均衡未开启）：

  • 查看网卡队列数（多队列网卡可分散中断压力）：
ethtool -l eth0  # 查看eth0的队列配置

输出示例（4 个接收队列、4 个发送队列）：

Channel parameters for eth0:
Pre-set maximums:
RX:             0
TX:             0
Other:          0
Combined:       4
Current hardware settings:
RX:             0
TX:             0
Other:          0
Combined:       4

  • 若队列数为 1（如Combined: 1），说明所有网络中断都集中在一个 CPU 上，容易导致软中断积压；

  • 查看网卡中断均衡状态：

ethtool -C eth0 | grep rx-usecs  # 查看接收中断均衡参数

若rx-usecs为 0，说明关闭了中断均衡（默认开启），可能导致小包频繁触发中断。

二、网络类软中断升高的解决方案（按优先级排序）​

1. 紧急处理：拦截异常流量（优先解决攻击 / 不合理请求）​

  • 若为 DDoS 攻击（如 SYN Flood、UDP Flood）：

  • 临时方案：通过iptables拦截异常 IP 或端口，示例（禁止所有 SYN 包，仅允许白名单 IP）：

iptables -A INPUT -p tcp --syn -j DROP  # 临时禁止SYN包（谨慎使用，会影响正常连接）
iptables -A INPUT -s 192.168.1.0/24 -p tcp --syn -j ACCEPT  # 允许白名单IP的SYN包

  • 长期方案：启用云服务商的 DDoS 防护（如阿里云 Anti-DDoS、腾讯云大禹），或部署硬件防火墙；

  • 若为应用层不合理请求（如频繁重试、无效接口调用）：

  • 临时方案：通过nginx限流（如限制单 IP 每秒请求数）：

limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;  # 单IP每秒最多10个请求
server \{
    location / \{
        limit_req zone=one burst=5;  # 允许突发5个请求
    \}
\}
  • 长期方案：优化应用层逻辑（如修复客户端重试机制、关闭无效接口）。

2. 系统优化：调整网卡与中断配置（分散 CPU 压力）​

  • 开启网卡多队列中断均衡（适用于多队列网卡）：

  • 确认网卡支持多队列后，绑定每个队列的中断到不同 CPU：

# 查看eth0的所有中断号（以eth0为例）
cat /proc/interrupts | grep eth0
# 输出示例：123: 123456 0 0 0  eth0-0；124: 0 45678 0 0  eth0-1（中断号123对应队列0，124对应队列1）
# 绑定中断123到CPU0，124到CPU1
echo 1 > /proc/irq/123/smp_affinity_list  # 1对应CPU0（二进制01）
echo 2 > /proc/irq/124/smp_affinity_list  # 2对应CPU1（二进制10）
  • 调整网卡中断触发阈值（减少小包触发的中断次数）：
ethtool -C eth0 rx-usecs 100  # 网卡接收缓冲区积累100微秒的数据后再触发中断
ethtool -C eth0 rx-frames 100  # 或积累100个数据包后触发中断（二选一即可）
  • 原理：通过 “批量处理” 减少中断触发次数，从而降低软中断 CPU 占用（注意：阈值过大会增加网络延迟，需根据业务平衡）。

3. 内核参数优化：提升网络处理能力​

调整/etc/sysctl.conf中的内核参数，优化网络栈性能：

# 增加网卡接收缓冲区大小（减少丢包）
net.core.netdev_max_backlog = 16384
net.core.somaxconn = 8192
# 增加TCP接收缓冲区大小
net.ipv4.tcp_rmem = 4096 87380 67108864
net.ipv4.tcp_wmem = 4096 65536 67108864
# 调整NET_RX软中断处理的数据包预算（默认300，增大减少软中断次数）
net.core.netdev_budget = 1000
# 启用TCP快速打开（减少连接建立延迟）
net.ipv4.tcp_fastopen = 3

执行sysctl -p使参数生效。

4. 架构优化：分流高流量（长期解决方案）​

  • 若为正常高流量（如电商大促、直播带货），需通过架构分流：

  • 增加服务器节点，通过负载均衡（如 Nginx、LVS）分散流量；

  • 使用 CDN 加速静态资源（如图片、视频），减少回源流量；

  • 引入消息队列（如 Kafka、RabbitMQ）异步处理请求，避免同步阻塞导致的流量堆积。

三、案例复盘：某电商服务器 NET_RX 软中断升高问题​

背景​

某电商服务器（8 核 16G，eth0 为 4 队列网卡）在大促期间出现si占比达 60%，服务器响应变慢，订单支付超时。

排查过程​

  1. top查看：si=62.3%，CPU0 和 CPU1 的si占比分别为 58% 和 55%；

  2. watch -n 1 cat /proc/softirqs：NET_RX每秒增长 15 万 +，其他软中断无明显增长；

  3. sar -n DEV 1 5：rxpck/s=16万+，rxkB/s=8000+（正常高流量，非攻击）；

  4. ethtool -l eth0：发现网卡队列数为 4，但/proc/interrupts显示所有中断都绑定在 CPU0 和 CPU1；

  5. 结论：网卡多队列未合理分配中断，导致 CPU0/1 软中断过载。

解决方案​

  1. 绑定网卡 4 个队列的中断到 CPU0-CPU3：
echo 1 > /proc/irq/123/smp_affinity_list  # 队列0→CPU0
echo 2 > /proc/irq/124/smp_affinity_list  # 队列1→CPU1
echo 4 > /proc/irq/125/smp_affinity_list  # 队列2→CPU2
echo 8 > /proc/irq/126/smp_affinity_list  # 队列3→CPU3

  1. 调整内核参数：net.core.netdev_budget=1000，net.core.netdev_max_backlog=16384；

  2. 扩容 2 台服务器，通过 Nginx 负载均衡分流流量。

效果​

  • si占比从 62.3% 降至 15% 以下；

  • 服务器响应时间从 500ms 降至 80ms；

  • 订单支付超时率从 3% 降至 0.1%。
