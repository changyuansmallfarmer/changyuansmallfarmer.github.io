ext3文件系统损坏问题分析

现象描述： 客户反馈一台项目机器在低温-40度实验完成后升至常温时对设备进行检查（通过PING网络的方式）时网络PING不通，随后将设备断电，再次上电发现系统无法正常启动。

问题定位

问题现象发生后，再次加电提示无法加载硬盘，确认系统无法启动是由于硬盘故障导致。使用winhex软件读取并分析故障硬盘上的原始数据，根据ext3文件系统的格式进行数据解析。 中标麒麟军用桌面操作系统（龙芯版）V5.0-B053在项目机器中使用ext3作为根文件系统。ext3文件系统在硬盘上保存数据的结构如下图： 图1 ext3文件系统结构 块（Block**）：硬盘中连续的一段存储位置，是硬盘读写数据的最小单位（存储的数据不足一个块时，也会占用一个块）。项目机器中，一个块的大小为4KiB（4096字节）。块的大小决定了整个文件系统的结构，下文介绍的各个属性均由块的大小算出。 索引节点（inode）：文件系统中给每个文件分配了索引节点，一个索引节点占用256字节，其中保存了该文件的属性(如权限、大小、时间戳等)，以及指向数据块的指针。 引导块（Boot Block）：位于分区上的第一个块中，占用1024字节（不足一个完整块）。里面存放的是boot loader，用于引导当前分区上的操作系统。 超级块（Super Block）：存储了整个文件系统的一些重要元数据，如各种时间戳、block总数量和空闲数量、inode总数量和空闲数量、当前文件系统是否正常等，占用1024字节。 如果block的大小为1KiB，则引导块正好占用一个block，这个block的序号为0，超级块的序号为1；如果block大小大于1K，则将引导块和超级块一起放在block 0中。项目环境就是第二种情况。 块组（Block Group）：将多个连续的块在逻辑上划分成一个块组，在文件系统读写数据时，先寻找块组，再寻找块组中对应的块，这样可以提高硬盘读写的效率。 块位图（Block Bitmap）：在文件系统读写数据时，需要知道硬盘分区中哪些块是有数据的，哪些块是空闲的。因此，在每个块组中需要有1个块来保存当前块组中所有块的使用情况，每个块用1位（1bit）来标识（0或1）。在块大小为4KiB时，块位图可以保存8*4096=32768个块的使用情况，即当前文件系统中，每个块组有32768个块。 索引节点表（inode table）：操作系统中文件的数量一般都会超过百万级，每次读写文件都遍历所有的inode，会严重影响IO速度，因此在每个块组中，维护了一个索引节点表，表中存储了当前块组中的存在的所有inode。 索引节点在文件系统初始化时（格式化）就已经创建，每个块组中分配了固定数量的inode，文件系统通过索引节点位图（inode Bitmap）可以获取当前块组中，哪些inode未使用，哪些inode已经被分配给文件。 块组描述符表（GDT）**：ext3文件系统将每一个块组信息使用32字节描述，这32个字节称为块组描述符，所有块组的块组描述符组成块组描述符表GDT(group descriptor table)。也就是说，GDT记录了整个硬盘分区中所有块组的元数据，通过GDT可以寻找到硬盘分区中的所有块。尽管在硬盘中保存了多份GDT，但在操作系统启动时，文件系统只使用块组 0中的GDT来获取硬盘分区信息。 读取文件流程： 以命令"cat /etc/a.conf"为例。 1）ext3文件系统预留了一些inode号，其中"/"的inode号为2，保存在块组0中。读取GDT可以知道块组0中inode table所在的块地址； 2）根据"/"的inode号查找inode table直接定位根目录文件的data block，在"/"的data block中记录了etc目录名和etc目录的inode号； 3）根据etc目录的inode号，计算出etc所在的块组编号，读取GDT获取此块组中inode table的位置，根据inode号找到etc目录文件对应的data block； 4）在etc目录文件的data block中记录了a.conf文件名和对应的inode号，通过该inode号定位到该inode所在的块组及所在的inode table，并根据该inode记录找到a.conf的data block； 5）最后读取a.conf的data block，获得文件内容。 当然，在每次定位到inode记录后，都会先将inode记录加载到内存中，然后查看权限，如果权限允许，将根据block指针找到对应的data block。 存储文件流程： 存储文件流程更复杂一些，数据要依次经过"内存脏页"、"硬盘缓存"以及"硬盘日志区"，才能最终写入到"硬盘存储块"中。 "内存脏页":操作系统在对磁盘上的文件进行修改时，数据不会立即回写到硬盘上，而是暂时保存在内存中。调用write往磁盘中写入数据时，先写到页中，将页标记为脏页，当出现页高速缓存空间不足、页变为脏页后长时间没有更新、进程通过系统调用sync同步数据等情况时，内核才会调用pd_flush将内存中的数据写回硬盘上。 "硬盘缓存":内存的IO速度远高于硬盘，如果将内存中的脏页数据直接写入硬盘，会导致写操作耗费很长时间。因此硬盘上引入了缓存机制，即在硬盘上额外安装一块内存条使用的存储颗粒当作缓冲区来暂存数据。而从缓冲区将数据写入实际硬盘采用无序写入方式（根据指针位置就近操作），也是为了提升硬盘IO性能。 "硬盘日志区"：ext3属于日志式文件系统。在创建ext3文件系统时，会在硬盘上划分一块日志区。每次当内存中的数据要写回硬盘时，会先记录本次写入的内容到日志区，然后再将日志区的数据写入最终的块中。这保证了写入数据过程中出现异常宕机，下次启动时也可以根据记录进行重演，保证了数据的完整性。 以命令"echo 1234 > /etc/b.conf"（b.conf不存在）为例，实际从日志区写入数据到"硬盘存储块"的流程如下： 1）读取GDT，找到各个(或部分)块组inode Bitmap中未使用的inode号，并为b.conf文件分配一个inode号，同时将b.conf文件名和对应的inode号添加到etc目录文件的data block中； 2）在对应的inode table中完善b.conf文件的信息，如权限，时间戳，文件大小等； 3）将数据填充到空闲的data block中，更新inode table中该文件inode记录中指向data block的寻址指针。 项目机器中根分区大小为30GiB，块大小为4KiB。即当前分区共有7864320个块（30GiB / 4KiB），分成240个块组（7864320 / 32768）；每个块组需要32字节描述，所以GDT表的大小为7680字节（32Byte * 240 = 7680Byte = 1.875块），需要2个块存储。 综上，根分区的Block 0（地址：0x00x0fff）保存了引导块和超级块的数据，Block 1（地址：0x10000x1fff）和Block 2（地址：0x20000x2fff）保存了GDT数据。 硬盘厂商对各个block的数据进行排查发现，Block 2中的GDT数据存在明显异常，有大量的0值存在。可以确定Block 2中的数据为错误数据。这将导致文件系统可以正常读取Block 1中的块组0127的数据，但不能正确读取到块组128至块组239中的数据。 图2 从故障硬盘读取的Block 2数据 Ext3文件系统给每个文件分配了inode号，根据inode号可以找到文件在硬盘上对应的存储位置。每个块组中包含的inode号数量是固定的。读取超级块得知，每个块组中包含了8192个inode号。也就是说，故障硬盘中，inode号大于1048576(8192 * 128块)的文件，无法正确读取。 图3 故障硬盘的超级块解析结果 使用硬盘中未损坏的GDT表覆盖Block 2的数据后，系统可以正常启动，查看启动目录/boot/得到各个文件的inode号。如图4，grub.efi、boot.cfg等引导文件的inode号均处于不能读取的范围。因此可以确认操作系统不能正常启动，是根分区的Block 2中GDT数据损坏，系统引导文件不能正确读取导致。 图4 从故障硬盘读取的Block 2数据

问题分析

中标麒麟桌面操作系统（龙芯版）的正常启动流程可以分为以下几个阶段：

  1. 龙芯平台常见BIOS有kunlun固件和PMON固件。BIOS启动结束后，kunlun固件从第一分区的/boot/grub.efi启动，然后加载启动菜单配置文件grub.cfg, PMON固件则直接加载第一分区的/boot/boot.cfg引导菜单配置文件并显示引导菜单；
  2. 根据所选的引导菜单选项，先加载对应的内核和内核启动参数到内存。再加载initramfs到内存中；
  3. 内核在内存中自解压并启动，对基础硬件做初始化。然后解压initramfs，形成一个临时根文件系统。
  4. 内核执行临时根文件系统中的/init程序，该程序是systemd的一个软连接。systemd程序启动之后，根据预设的运行级别加载对应的服务，为操作系统启动进行一系列的环境准备。其中systemd-fsck-root服务用来对硬盘进行检查，对未完成的操作进行日志重演。最后再以读写模式挂载硬盘分区。
  5. systemd依次加载服务直到登录界面显示，此时用户可以使用账号密码登录到系统桌面，结束开机流程。

在阶段4挂载分区前，会对硬盘做fsck，当出现文件系统损坏时，会对硬盘数据进行修复。当硬盘修复过程中将错误的日志进行重演时，如果损坏了系统启动相关的数据，不会对本次启动造成影响（因为对应的文件已经加载到内存），但会导致在下次启动阶段出现提示"无法加载硬盘"的错误。

ext3文件系统有内建日志功能，在硬盘分区中单独保留一块空间，用来记录硬盘数据的修改记录。在逻辑上，这块空间是环形存储区域，最后一条记录会覆盖最初的记录。写数据到硬盘时，会先记录本次要操作的块对象和需要写入的数据，然后再真正地写入数据到对应的块中。

如图5，查看文件系统的操作记录，最后一条记录的seq号为150082（十六进制为0x024A42），硬盘中的首地址为0x3B8444000。该记录中第10条为Block 2的操作，根据记录的首地址和偏移值，计算得到Block 2中被写入的数据地址为0x3B844D000（0x3B8444000 + 10 * 4KiB），查看该地址中的数据，与Block 2中的数据相同（图6中的数据与图2中的数据相同），因此可以确定Block 2的错误数据是因为重演文件系统记录得到的。

图5 损坏硬盘中文件系统的最后记录

图6 文件系统记录的数据

根据GDT的特点，Block 2中的数据不应该如图中所示出现大量0值（0值会导致识别不到硬盘中对应地址的存储块），所以此记录对应的Block 2的数据是错误的。

当写数据过程中遇到突然断电等异常情况时，可能会导致需要写入到硬盘对应块中的数据不完整（此时文件系统认为写操作未完成）。下次系统启动，在挂载硬盘前，检查到文件系统存在未完成任务，会根据日志记录进行重演，重新写入硬盘。如图5所示，577590是一条完整的日志记录，577和590分别代表记录的开始和结束，中间为要写入的块和数据。但是记录在写入到硬盘时并非是依次逐条写入：577和590两条记录先写入硬盘，中间的实际操作数据可能会后写入。这种情况下，如果在578579数据写入过程中出现了断电等异常状况，那么这些数据写入不完整，部分内容是上次使用该Block时残留的数据。再次开机时，在硬盘挂载前做文件系统检查时，发现有未完成的写入操作，将根据硬盘中的日志记录(579~590)进行重演，从而导致GDT数据（Block 2）被损坏。

修复故障硬盘的GDT数据后进入操作系统。查看系统日志发现，在操作系统日志的最后阶段出现频繁重启，并且这些重启过程中，没有正常的关机日志，属于异常掉电现象。

当前操作系统预设的安装分区布局是：第一分区作为根分区，第三分区作为备份还原分区，第五分区作为用户数据分区挂载到/home文件夹。操作系统在启动过程中，会读取硬盘上的数据，同时也会写数据到硬盘，如/var/目录下的一些状态文件、开关机相关的日志记录等。当写硬盘操作过程中机器断电，会导致文件系统写入数据不完整，出现文件系统损坏的现象，需要在下次启动时根据记录进行重演。如果重演了错误的硬盘日志造成根分区数据损坏（如GDT、超级块等元数据损坏），间接导致boot目录下内核和initramfs文件无法识别，就会导致无法加载内核和initramfs文件，系统无法正常启动。

可以通过设置单独的boot分区，把系统启动需要加载的内核和initramfs文件放在这个单独的分区。系统启动相关的文件和数据一般不做修改，就没有写操作，即使出现异常掉电也不会对boot分区数据造成损坏。当其他分区数据出现损坏的情况下，也不会影响到boot分区的数据。在开机过程中，如果检测到根分区文件系统出现损坏，则触发自动修复机制，只对根分区上的数据做恢复，可以避免根分区数据损坏导致的无法启动。

结论与建议

项目机器在出现问题前有频繁掉电现象，最后一次不能启动是异常掉电导致产生了错误的数据记录，文件系统根据此记录进行了重演，导致GDT数据损坏，无法识别到操作系统引导文件导致。 建议在使用过程中应避免异常掉电，使用正常的关机流程，保证硬盘数据完整性，避免触发ext3文件系统缺陷导致数据损坏。
