Linux内核arm64内存的工作原理

[TOC]

前言：为什么要理解 arm64 内存工作原理？​

随着 ARM 架构在服务器、嵌入式设备中的广泛应用，Linux arm64 成为主流操作系统之一。内存作为系统核心资源，其管理机制直接影响应用程序的稳定性和性能 —— 内存泄漏、OOM 崩溃、缓存失效等问题，本质上都与内存工作原理相关。本文将从普通进程的视角出发，拆解 arm64 架构下 Linux 内存的核心逻辑：虚拟内存与物理内存的映射机制、虚拟地址空间分布、进程内存申请的底层实现、内存不足时的系统应对策略，以及实用的内存监控工具，帮你从根源理解内存相关问题。

一、核心基础：虚拟内存与物理内存的映射关系​

对于 Linux 系统中的普通进程而言，它永远无法直接访问物理内存，只能看到内核提供的 “虚拟内存地址空间”。这种设计的核心目的是：隔离进程地址空间（避免进程间相互干扰）、突破物理内存限制（虚拟地址空间远大于物理内存）、简化内存管理（统一地址分配逻辑）。

1. 虚拟内存与物理内存的核心区别​

维度虚拟内存物理内存
可见性进程私有，每个进程独立拥有完整地址空间系统全局共享，内核统一管理
大小限制由 CPU 位数决定（arm64 为 64 位，理论支持 16EB）由硬件配置决定（如服务器通常为 32GB/64GB/128GB）
作用进程代码、数据的 “逻辑地址载体”实际存储数据的 “物理硬件空间”

2. 映射的核心：页表（Page Table）与 MMU/TLB​

虚拟内存到物理内存的映射，依赖于页表这一关键数据结构 —— 页表由内核维护，记录了虚拟页（Virtual Page）与物理页（Physical Page）的对应关系。arm64 架构下的映射机制有三大关键组件：

  • 页表特性：采用 4 级或 5 级多级页表（减少页表内存占用），支持 4KB/16KB/64KB 普通页和 2MB/1GB 大页（HugePage），大页可降低页表项数量，提升映射效率；

  • MMU（内存管理单元）：CPU 内置硬件组件，负责查询页表并完成虚拟地址到物理地址的转换，避免软件层面的低效查询；

  • TLB（转译后备缓冲器）：MMU 中的页表高速缓存，存储最近使用的映射关系。由于进程地址空间独立，切换进程会刷新 TLB，因此减少上下文切换可提升 TLB 命中率，进而优化内存访问性能。

3. 映射过程：从虚拟地址到物理地址的转换​

  1. 当进程访问某个虚拟地址时，整个映射流程如下：

  2. 进程发起内存访问请求（如读取变量、执行代码），传入虚拟地址；

  3. CPU 的 MMU 接收请求，先查询 TLB 缓存，若命中则直接转换为物理地址访问内存；

  4. 若 TLB 未命中，MMU 查询当前进程的多级页表；

  5. 若页表中存在对应物理页（即 “页命中”），MMU 将映射关系写入 TLB，再访问物理内存；

  6. 若页表中无对应记录（即 “缺页”），MMU 触发缺页异常，陷入内核态；

  7. 内核处理缺页异常：分配物理内存、更新页表，建立虚拟页与物理页的映射；

  8. 回到用户态，进程继续访问内存（此时已映射成功）。

二、虚拟内存空间分布：用户空间与内核空间的划分​

arm64 架构的虚拟地址空间总大小为 256TB，分为内核空间和用户空间两部分，各占 128TB，中间为未定义区域。进程在用户态仅能访问用户空间，进入内核态后才可访问内核空间（所有进程的内核空间映射到同一块物理内存）。

用户空间128T0x0000000000000000 - 0x00007FFFFFFFF000
未定义
内核空间128T0xFFFF8000000000000 - 0xFFFFFFFFFFFFFFFF

用户空间的五大内存段（从低地址到高地址）​

内存段作用特性
只读段存储代码（.text）、常量（.rodata）不可修改，防止误操作破坏程序逻辑
数据段存储全局变量、静态变量（.data/.bss）程序启动时初始化，占用物理内存
堆动态分配内存（如 malloc () 申请的小块内存）从低地址向上增长，可动态扩展
文件映射段存储动态库、共享内存、mmap () 分配的大块内存从高地址向下增长，释放后直接归还系统
栈存储局部变量、函数调用上下文大小固定（默认 8MB），向下增长，溢出会导致栈崩溃

关键说明​

  • 堆和文件映射段是动态分配的核心区域：小块内存（）通过堆分配，大块内存（>128K）通过文件映射段分配；

  • 内核空间位于虚拟地址最高位，包含内核代码、内核数据、物理内存映射表等，仅内核态可访问。

三、进程内存申请：malloc () 的底层实现与延迟分配​

很多开发者会有一个误区：调用malloc()申请内存后，系统会立即分配物理内存。但在 Linux 中（包括 arm64 架构），内存分配遵循 “延迟分配” 原则 ——malloc () 仅分配虚拟内存，物理内存直到首次访问时才会真正分配。

1. malloc () 的两种底层实现：brk () 与 mmap ()​

malloc () 是 C 标准库提供的内存分配函数，底层依赖内核的两种系统调用，根据内存大小自动选择：

  • 小块内存（小于128K）：使用brk()系统调用，通过移动堆顶指针（_edata）来分配内存。释放后不会立即归还系统，而是缓存起来重复利用，减少缺页异常，但可能产生内存碎片；

  • 大块内存（大于128K）：使用mmap()系统调用，在文件映射段分配空闲内存。释放后直接归还系统，无内存碎片，但每次分配都会触发缺页异常，内核管理开销较大。

2. 内存申请与分配的完整流程（以 malloc (1024) 为例）​

  1. 进程调用malloc(1024)，C 标准库判断为小块内存，调用brk()向内核请求虚拟内存；

  2. 内核检查进程的堆空间，找到 1KB 空闲虚拟内存，标记为 “已分配”，返回虚拟地址给进程（无物理内存分配）；

  3. 进程首次访问该虚拟地址（如*addr = 10），触发缺页异常；

  4. 内核通过伙伴系统分配 1 个 4KB 物理页（页为内存分配最小单位），建立虚拟页与物理页的映射；

  5. 若申请的内存小于 4KB（如 1KB），内核通过slab 分配器将物理页划分为小内存块，仅分配所需大小，避免内存浪费；

  6. 物理内存分配完成，进程成功写入数据。

3. 内核的内存管理机制：伙伴系统与 slab 分配器​

  • 伙伴系统：内核用于管理物理内存的核心机制，以页为单位分配内存，通过合并相邻空闲页减少内存碎片（解决 brk () 导致的碎片问题）；

  • slab 分配器：构建在伙伴系统之上，用于分配内核中的小对象（如进程描述符、文件结构体）和用户空间的小块内存，通过缓存常用大小的内存块，提升分配效率。

4. 延迟分配的核心优势与注意事项​

  • 优势：避免内存浪费（未使用的虚拟内存不占用物理内存）、提升申请效率（仅修改内核数据结构）、支持超物理内存的虚拟内存申请；

  • 注意：malloc()返回非 NULL 不代表物理内存可用，若系统物理内存耗尽，首次访问虚拟地址时会触发 OOM 崩溃。

四、内存不足时的系统应对机制​

Linux arm64 的虚拟地址空间远大于物理内存，当多个进程同时使用物理内存，导致物理内存不足时，系统会通过三层机制保障稳定运行：

1. 缓存回收：释放可回收内存​

Linux 会将部分物理内存用作页缓存（Page Cache）、目录项缓存（dentry Cache） 和inode 缓存，用于缓存磁盘文件数据，加速后续访问。当物理内存不足时：

  • 内核的kswapd线程后台扫描缓存，采用 LRU（最近最少使用）算法回收不常用的缓存页；

  • 可回收缓存不包含进程私有数据、内核栈等，回收后不影响程序运行；

  • 手动回收命令：

    echo 3 > /proc/sys/vm/drop_caches（生产环境慎用，会导致缓存失效）。

2. 交换分区（Swap）：物理内存的 “延伸”​

Swap 是磁盘上的特殊分区，作为物理内存的补充，核心作用是 “换出不常用内存，释放物理内存给活跃进程”：

  • 换出：将进程不常用的物理页写入 Swap；

  • 换入：进程访问已换出的内存时，从 Swap 读回物理内存；

  • 配置方法：mkswap /dev/sdb1（创建）、swapon /dev/sdb1（启用），永久启用需修改/etc/fstab；

  • 注意：Swap 读写速度比物理内存慢 1000 倍，频繁换入换出（Swap Thrashing）会导致系统卡顿，建议大小设为物理内存的 1-2 倍，仅在内存峰值波动场景使用。

3. OOM killer：内存耗尽时的 “最后手段”​

当物理内存和 Swap 都耗尽，且无缓存可回收时，内核触发 OOM killer 机制：

  • 评分机制：通过oom_score评估进程优先级，oom_score = 进程内存占用率 × 10 + oom_score_adj；

  • 决策逻辑：优先杀死oom_score最高的进程（内存占用多、CPU 使用率低的进程）；

  • 手动调整：通过echo -1000 > /proc/[PID]/oom_adj（范围 - 17~15）设置进程的 OOM 优先级，-17 表示禁止被 OOM 杀死（核心服务推荐配置）；

  • 日志查询：OOM 触发后，可通过dmesg | grep -E 'kill|oom|out of memory'查看被杀死的进程。

五、内存监控工具：free、top、ps 的实战用法​

了解内存工作原理后，需通过工具监控系统和进程的内存使用情况，定位内存泄漏、高缓存占用等问题。以下是最常用的 3 个工具，重点解析 arm64 环境下的关键指标。

1. free：查看系统整体内存状态​

free用于查看系统物理内存、Swap、缓存的使用情况，核心命令：free -h（-h 表示人性化显示单位）。

输出结果解析（arm64 环境示例）​

              total        used        free      shared  buff/cache   available
Mem:           62Gi       8.5Gi        45Gi       1.2Gi       8.5Gi        52Gi
Swap:          31Gi          0B        31Gi

  • 核心指标：available（可被新进程使用的内存）= 空闲内存 + 可回收缓存，是判断系统内存是否充足的关键（而非free）；

  • 误区纠正：Linux 会主动使用空闲内存作为缓存，因此free值小不代表内存紧张，只要available充足即可。

2. top：实时监控进程内存占用​

top是实时进程监控工具，按M键可按内存占用排序，重点关注以下指标：

指标含义说明
%MEM进程占用物理内存的百分比反映进程内存消耗的相对比例
VIRT进程虚拟内存大小包含所有申请过的内存（未分配物理内存的部分也计算在内）
RES常驻内存大小进程实际使用的物理内存（不含 Swap 和共享内存），核心指标
SHR共享内存大小包含共享库、进程间共享内存，非进程独占，不可直接累加

关键结论​

  • 判断进程真实内存占用，优先看RES而非VIRT（虚拟内存可能包含大量未使用空间）；

  • 共享内存SHR不一定被多个进程共享，程序代码段、非共享动态库也会计入，因此不能通过SHR直接计算进程间共享内存总量。

3. ps：查看进程内存详细信息​

ps用于查询进程的静态内存状态，常用命令：ps -aux --sort=-%mem（按内存占用降序排列）。

重点关注字段​

  • %mem：与 top 的 % MEM 一致；

  • vsize：虚拟内存大小（对应 top 的 VIRT）；

  • rss：常驻内存大小（对应 top 的 RES）；

  • 实用技巧：结合grep筛选特定进程（如ps -aux | grep java），或通过pmap -x [PID]查看进程的内存段分布，定位异常内存占用。

工具使用流程​

  1. 快速判断系统内存状态：free -h → 看available；

  2. 定位高内存占用进程：top（实时）或ps -aux --sort=-%mem（静态）；

  3. 分析进程内存细节：pmap -x [PID] 或 cat /proc/[PID]/status；

  4. 排查 OOM 问题：dmesg | grep oom 查看历史 OOM 日志。

六、核心总结​

  1. 地址隔离与映射：arm64 进程通过虚拟地址访问内存，经页表 + MMU 映射到物理内存，TLB 缓存可优化映射效率；

  2. 延迟分配与底层机制：malloc () 仅分配虚拟内存，物理内存在首次访问时通过缺页异常分配，底层依赖 brk ()/mmap () 系统调用和伙伴系统 /slab 分配器；

  3. 内存不足应对：系统通过 “缓存回收→Swap 换入换出→OOM killer” 三层机制保障稳定，核心服务需配置 OOM 保护；

  4. 监控核心逻辑：系统层面看available（free），进程层面看RES（top/ps），避免被虚拟内存或缓存占用误导。

理解 Linux arm64 内存工作原理，能帮你从根源解决内存泄漏、OOM、Swap 抖动等问题。后续可进一步学习内存泄漏排查工具（如 valgrind、pprof）、大页内存配置、缓存优化等进阶内容，让内存管理更精细化。
