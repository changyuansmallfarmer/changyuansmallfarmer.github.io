linux如何定位swap升高的问题

前言：Swap 升高的潜在风险​

Swap 作为 Linux 内存管理的重要机制，本质是 “磁盘充当内存扩展”—— 当物理内存紧张时，系统会将不常访问的匿名页换出到磁盘，需要时再换入内存。但 Swap 升高往往伴随性能隐患：磁盘 I/O 延迟远高于内存，频繁的换入换出（Swap Thrashing）会导致系统响应变慢、CPU 等待 I/O 时间增加，严重时影响应用可用性。

本文基于 Ubuntu 18.04 环境（兼容 CentOS 等主流发行版），带你掌握从 “确认 Swap 升高” 到 “定位根源” 再到 “优化解决” 的全流程，核心工具包括free、sar、/proc/zoneinfo等。

一、先搞懂：Swap 升高的核心原因​

在定位前，需明确 Swap 升高的底层逻辑（参考文档核心知识点）：

  1. 内存回收触发：当系统剩余内存低于页低阈值（pages_low）时，内核会通过kswapd0线程或直接内存回收，释放可回收内存。其中：

  • 文件页（缓存 / 缓冲区）：可直接回收或写回磁盘后回收；

  • 匿名页（应用堆内存）：需通过 Swap 换出到磁盘回收。

  1. 回收倾向控制：swappiness参数（0-100）调整回收倾向：数值越大，越倾向于回收匿名页（触发 Swap）；数值越小，越倾向于回收文件页。即使swappiness=0，当剩余内存 + 文件页＜页低阈值时，仍会触发 Swap。

  2. NUMA 架构影响：多 Node 服务器中，若某 Node 本地内存不足，默认会从其他 Node 申请内存或本地回收，若配置zone_reclaim_mode=4，则优先通过 Swap 回收本地匿名页。

二、第一步：确认 Swap 升高（量化问题）​

首先需通过工具验证 Swap 确实在增长，而非单次快照的误判，同时排除正常场景（如系统休眠）。

必备工具：free（快速查看 Swap 状态）​

# 查看内存与Swap整体使用情况
free -h

输出示例与解读​

              total        used        free      shared  buff/cache   available
Mem:           7.8Gi       3.2Gi       1.5Gi       696Ki       3.1Gi       4.3Gi
Swap:          8.0Gi       2.3Gi       5.7Gi

  • 关键判断：Swap used持续增长（如每小时增加 500MB+），且Mem free持续偏低（＜总内存的 10%），说明 Swap 升高是内存压力导致；

  • 排除缓存干扰：执行echo 3 > /proc/sys/vm/drop_caches清理缓存后，若Mem free回升但Swap used未下降，说明是匿名页换出导致的 Swap 升高。

辅助工具：sar（实时监控 Swap 变化）​

sar可跟踪内存、Swap 的动态变化，精准捕捉升高趋势：

# 安装sysstat（若未安装）
sudo apt-get install -y sysstat

# 间隔1秒输出1组数据，持续监控（-r：内存，-S：Swap）
sar -r -S 1

关键指标解读（重点关注 Swap 相关字段）​

04:39:57 kbswpfree kbswpused %swpused kbswpcad %swpcad
04:39:58 8388604    0        0.00     0        0.00
04:39:59 8123456    265148   3.16     0        0.00
04:40:00 7856320    532284   6.34     0        0.00

  • kbswpused：已使用的 Swap 大小（持续增长为异常特征）；

  • %swpused：Swap 使用率（超过 50% 需重点关注）；

  • kbswpcad：被缓存的 Swap 数据（非零表示部分 Swap 数据已换入内存）。

三、第二步：定位 Swap 升高的根源​

确认 Swap 升高后，需进一步排查 “为什么触发 Swap”（内存回收原因）和 “哪些进程被换出”（受影响对象）。

1. 排查内存回收触发原因：/proc/zoneinfo​

通过/proc/zoneinfo查看内存阈值与内存域状态，判断是否因内存不足触发回收：

# 高亮显示变化字段，仅查看Normal内存域的关键信息
watch -d grep -A 15 'Normal' /proc/zoneinfo

核心字段解读（以 Node 0 的 Normal 域为例）​

Node 0, zone Normal
  pages free     21328  # 剩余内存页（与nr_free_pages一致）
  min            14896  # 页最小阈值
  low            18620  # 页低阈值（触发回收）
  high           22344  # 页高阈值（回收目标）
  nr_zone_inactive_anon 79776  # 非活跃匿名页（易被Swap换出）
  nr_zone_active_anon 206854   # 活跃匿名页（难被回收）
  nr_zone_inactive_file 918561 # 非活跃文件页（易被回收）
  nr_zone_active_file 496695   # 活跃文件页（难被回收）

关键判断逻辑​

  • 当pages free＜low时，系统触发内存回收：若nr_zone_inactive_anon较多，会优先换出匿名页（导致 Swap 升高）；

  • 若pages free在low与high之间波动，说明系统处于 “回收 - 分配” 循环，需进一步查看占用内存的进程。

2. 定位占用内存的进程：top/ps​

Swap 升高的本质是物理内存不足，需找到消耗内存的 “元凶”：

# top实时监控（按M键排序，关注%MEM和RSS）
top

# ps按物理内存占用降序输出（前10个进程）
ps -aux --sort=-%mem | head -10

重点关注进程特征​

  • %MEM持续升高，且RSS（常驻物理内存）接近进程申请的内存大小；

  • 排除缓存进程（如nginx缓存静态文件），重点关注应用进程（如 Java、Python 服务）。

3. 确认被 Swap 换出的进程：/proc/pid/status​

通过VmSwap字段查看单个进程的 Swap 使用量，定位受影响的应用：

# 遍历所有进程，按VmSwap大小排序（输出进程名、PID、Swap用量）
for file in /proc/*/status; do
  awk '/VmSwap|Name|^Pid/{printf $2 " " $3} END{print ""}' $file
done | sort -k3 -nr | head -10

输出示例与解读​

dockerd 2226 10728 kB
docker-containe 2251 8516 kB
snapd 936 4020 kB
networkd-dispat 911 836 kB

  • 若应用进程的VmSwap较大（如超过 100MB），说明其内存被频繁换出，会导致应用响应变慢；

  • 优先处理核心业务进程（如数据库、API 服务）的 Swap 换出问题。

4. 检查回收倾向配置：swappiness​

# 查看当前swappiness配置（默认60）
cat /proc/sys/vm/swappiness

配置解读​

  • swappiness=60：系统平衡回收文件页和匿名页，易因匿名页过多触发 Swap；

  • swappiness=10：倾向于回收文件页，减少 Swap 使用（适合内存充足的服务器）；

  • swappiness=0：最大限度避免 Swap，但内存紧张时仍会触发（内核≥3.5）。

四、实战案例：复现 Swap 升高并定位​

基于参考文档的 dd 案例，模拟大文件读取导致的 Swap 升高，完整演示定位流程：

案例环境​

  • 配置：2CPU+8GB 内存，Ubuntu 18.04，已创建 8GB Swap 文件；

  • 触发命令：dd if=/dev/sda1 of=/dev/null bs=1G count=2048（模拟大文件读取，占用大量缓存）。

步骤 1：监控 Swap 变化​

# 终端1：运行dd命令
dd if=/dev/sda1 of=/dev/null bs=1G count=2048

# 终端2：用sar监控内存与Swap
sar -r -S 1

现象观察​

  • 初期：Mem used持续增长，buff/cache快速升高（缓存大文件数据）；

  • 后期：Mem free＜页低阈值，kbswpused开始增长（系统换出匿名页）；

  • %swpused逐渐上升至 10%+，wa（CPU 等待 I/O）升高至 5%+。

步骤 2：用 cachetop 查看缓存占用​

# 5秒刷新一次，查看进程缓存命中情况
cachetop 5

输出关键信息​

12:28:28 Buffers MB: 6349 / Cached MB: 87 / Sort: HITS / Order: ascending
PID  UID  CMD    HITS  MISSES  DIRTIES  READ_HIT%  WRITE_HIT%
18280 root dd     41088 41022   0        50.0%      0.0%
  • 解读：dd 进程的缓存命中率仅 50%，大量未命中请求导致缓存持续增长，挤压物理内存，触发 Swap。

步骤 3：定位被换出的进程​

# 查看Swap使用最多的进程
for file in /proc/*/status; do
  awk '/VmSwap|Name|^Pid/{printf $2 " " $3} END{print ""}' $file
done | sort -k3 -nr | head -5

输出结果​

dockerd 2226 10728 kB
docker-containe 2251 8516 kB
snapd 936 4020 kB
  • 解读：dockerd 和 docker 容器进程的内存被换出到 Swap，若后续访问这些进程，会出现明显延迟。

案例结论​

本案例中 Swap 升高的根源是：大文件读取导致缓存占用过多物理内存，系统为释放内存，将不活跃的匿名页（如 docker 进程内存）换出到 Swap。

五、第三步：Swap 升高的优化方案​

根据定位结果，可通过以下方法降低 Swap 使用，提升系统性能：

1. 紧急处理：清理 Swap 空间​

若 Swap 使用率过高（＞80%），可临时清理 Swap（需确保物理内存充足）：

# 关闭并重新开启Swap（会将Swap数据换入内存，需预留足够内存）
swapoff -a && swapon -a
  • 风险提示：若物理内存不足，执行后可能触发 OOM，建议低峰期操作。

2. 短期优化：调整 swappiness​

降低swappiness值，减少系统换出匿名页的倾向：

# 临时调整（重启失效）
echo 10 > /proc/sys/vm/swappiness

# 永久调整（编辑/etc/sysctl.conf，添加以下配置）
echo "vm.swappiness = 10" >> /etc/sysctl.conf
sysctl -p  # 生效配置
  • 推荐值：服务器场景建议 10-30，嵌入式设备可设为 0（内存紧张时仍会触发 Swap）。

3. 中期优化：优化内存使用​

  • 关闭不必要的进程：终止空闲的大内存进程（如闲置的容器、备份程序）；

  • 限制应用内存：通过cgroups或应用自身配置，限制进程最大内存占用（如 Java -Xmx参数）；

  • 清理无效缓存：避免大文件一次性读取（如 dd 案例），或使用posix_fadvise告知系统无需缓存：

#include 
posix_fadvise(fd, 0, 0, POSIX_FADV_NOREUSE);  // 告知系统文件仅读取一次

4. 长期优化：硬件与架构调整​

  • 增加物理内存：若 Swap 频繁升高，说明内存不足，建议扩容（如从 8GB 增至 16GB）；

  • 调整 NUMA 策略：多 Node 服务器中，设置zone_reclaim_mode=0（默认），允许跨 Node 申请内存：

echo 0 > /proc/sys/vm/zone_reclaim_mode
  • 禁用 Swap（推荐云服务器）：大部分云平台默认禁用 Swap，避免磁盘 I/O 影响性能：
# 临时禁用
swapoff -a

# 永久禁用（编辑/etc/fstab，注释Swap配置行）
sed -i '/swap/s/^/#/' /etc/fstab

5. 核心业务保护：锁定内存​

对响应延迟敏感的应用（如数据库、实时计算服务），可锁定内存，阻止其被换出：

# 方法1：使用mlockall()系统调用（应用代码中添加）
#include man.h>
mlockall(MCL_CURRENT | MCL_FUTURE);  // 锁定当前和未来分配的内存

# 方法2：通过prlimit设置进程锁定内存上限
prlimit --pid [PID] --memlock=unlimited

六、常见问题排查：Swap 升高但内存充足？​

若free显示剩余内存较多（＞20%）但 Swap 仍升高，大概率是 NUMA 架构导致：

查看 NUMA 节点内存使用：

numactl --hardware  # 查看Node分布
numastat -m          # 查看各Node内存使用

问题原因：某 Node 本地内存不足，即使其他 Node 有空闲内存，系统仍会换出本地匿名页；

解决方法：设置zone_reclaim_mode=0，允许跨 Node 申请内存（默认配置，若被修改需重置）。

七、核心总结​

  1. 确认问题：用free+sar监控 Swap 是否持续增长，排除缓存干扰；

  2. 定位根源：

    • 用/proc/zoneinfo查看内存阈值，判断是否因内存不足触发回收；

    • 用ps+/proc/pid/status找到占用内存和被换出的进程；

    • 用cachetop排查缓存占用是否异常；

  3. 优化方案：优先调整swappiness和清理无效内存，长期考虑扩容或禁用 Swap；

  4. 核心原则：Swap 升高是内存压力的 “结果”，而非 “原因”，需从内存使用源头解决问题。
