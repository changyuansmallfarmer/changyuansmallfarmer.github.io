一、用户空间中的延迟测量

当用户应用程序开发人员正在处理对性能敏感的代码时，一个常见的需求是测量代码中的延迟或时间。这种类型的代码可以临时用于调试、测试或分析目的，或者永久地用于在软件生产模式中提供性能跟踪数据。 Linux内核提供了gettimeofday()和clock_gettime()系统调用，用于用户应用程序中的高分辨率时间测量。gettimeofday()提供微秒级的分辨率，而clock_gettime()提供纳秒级的分辨率。然而，使用这些系统调用时的一个主要问题是，函数调用本身的开销会带来额外的性能成本。 为了最小化gettimeofday()和clock_gettime()系统调用的性能成本，Linux内核使用vsycall(virtual system calls)和vdso(Virtual Dynamically linked Shared Objects)机制来避免从用户空间切换到内核空间的开销。在x86架构上，gettimeofday()和clock_gettime()可以获得更好的性能，因为vsycalls内核补丁避免了上下文从用户空间切换到内核空间。然而，在其他一些体系结构上，仍然需要遵循常规的系统调用代码路径。这种优化实际上依赖于硬件。 对于TSC的大多数用例，gettimeofday()和clock_gettime()的vsycall可以避免用户空间和内核空间之间的上下文切换，并尝试使用rdtsc指令直接获取TSC寄存器值，从而减少主要的性能开销。此外，这些系统调用提供了更好的可移植性和错误处理能力。例如，可以通过gettimeofday()和clock_gettime() vsycall来解决可能在多个cpu之间没有检测到的TSC同步问题。

二、为什么我们应该使用tsc

尽管gettimeofday()和clock_gettime()的vsycall实现比常规系统调用更快，但它们的性能成本仍然太高，无法满足某些对性能敏感的应用程序的延迟测量需求。 x86处理器提供的TSC(时间戳计数器)是一种高分辨率计数器，可以用一条指令(RDTSC)读取。在Linux上，该指令可以直接从用户空间执行，这意味着用户应用程序可以使用一条指令以比vsycalls快得多的方式获得细粒度的时间戳(纳秒级)。 以下代码是rdtsc() api在用户空间应用程序中的典型实现:

static uint64_t rdtsc(void)
{
    uint64_t var;
    uint32_t hi, lo;

    __asm volatile
        ("rdtsc" : "=a" (lo), "=d" (hi));

    var = ((uint64_t)hi << 32) | lo;
    return (var);
}

rdtsc函数的结果是CPU周期，通过简单的计算可以将其转换为纳秒。

ns = CPU cycles * (ns_per_sec / CPU freq)

在Linux内核中，它使用更复杂的方法来获得更好的结果，

/*
 * Accelerators for sched_clock()
 * convert from cycles(64bits) => nanoseconds (64bits)
 *  basic equation:
 *              ns = cycles / (freq / ns_per_sec)
 *              ns = cycles * (ns_per_sec / freq)
 *              ns = cycles * (10^9 / (cpu_khz * 10^3))
 *              ns = cycles * (10^6 / cpu_khz)
 *
 *      Then we use scaling math (suggested by george@mvista.com) to get:
 *              ns = cycles * (10^6 * SC / cpu_khz) / SC
 *              ns = cycles * cyc2ns_scale / SC
 *
 *      And since SC is a constant power of two, we can convert the div
 *  into a shift.
 *
 *  We can use khz divisor instead of mhz to keep a better precision, since
 *  cyc2ns_scale is limited to 10^6 * 2^10, which fits in 32 bits.
 *  (mathieu.desnoyers@polymtl.ca)
 *
 *                      -johnstul@us.ibm.com "math is hard, lets go shopping!"
 */

最后，延时测量代码为:

start = rdtsc();
/* put code you want to measure here */
end = rdtsc();
cycle = end - start;
latency = cycle_2_ns(cycle)

实际上，上面的rdtsc实现都是有问题的，并且不受Linux内核的鼓励。主要原因是TSC机制非常不可靠，即使是Linux内核也很难处理它。 这就是Linux内核不向用户应用程序提供rdtsc api的原因。然而，Linux内核并不限制rdtsc指令在特权级别执行，尽管x86支持这种设置。这意味着，没有什么可以阻止Linux应用程序通过上述实现直接读取TSC，但是由于一些已知的陷阱，这些应用程序必须准备处理一些奇怪的TSC行为。

三、已知的TSC缺陷

3.1 不稳定的TSC硬件​

3.1.1 CPU的TSC能力​

英特尔cpu有三种特性的TSC （1）可变TSC 在第一代TSC中，TSC增量可能会受到CPU频率变化的影响。这是从一个非常老的处理器(P4)开始的。 （2）恒定TSC TSC以恒定的速率增加，甚至CPU频率也会发生变化。但是TSC可以在CPU运行到深c状态时停止。在Nehalem之前支持恒定TSC，但不如不变TSC好。 （3）不变TSC 不变的TSC将在所有ACPI P-、C-和t状态下以恒定速率运行。这是向前发展的体系结构行为。不变TSC只出现在nehalem和后来的Intel处理器上。 参见Intel 64 Architecture SDM Vol. 3A“17.12.1 Invariant TSC”。 Linux根据CPU的不同定义了几个CPU特性位，

  • X86_FEATURE_TSC TSC在CPU中可用。
  • X86_FEATURE_CONSTANT_TSC 具有恒定tsc
  • X86_FEATURE_NONSTOP_TSC CPU在C-state 不会停止 CONSTANT_TSC和NONSTOP_TSC标志组合对不变TSC是启用的。请参考这个内核补丁来实现。 如果CPU没有“不变TSC”特性，当内核启用P或C状态时，可能会导致TSC问题:turbo boost, speed-step, or CPU power management features.。 例如，如果Linux内核没有检测到NONSTOP_TSC特性，当CPU运行到深度睡眠c状态时，为了省电，Intel空闲驱动会尝试将TSC标记为不稳定标志。
if (((mwait_cstate + 1) > 2) &&
    !boot_cpu_has(X86_FEATURE_NONSTOP_TSC))
    mark_tsc_unstable("TSC halts in idle"
            " states deeper than C2");

ACPI CPU空闲驱动程序具有类似的逻辑来检查NONSTOP_TSC是否为深度睡眠c状态。 请在Linux上使用下面的命令来检查CPU能力。

cat  /proc/cpuinfo | grep -E "constant_tsc|nonstop_tsc"
  • X86_FEATURE_TSC_RELIABLE 一个合成标志，TSC同步检查被跳过。 CPU特征位只能表示UP系统中TSC的稳定性。对于SMP系统，没有明确的方法可以保证TSC的可靠性。TSC同步测试是测试SMP TSC可靠性的唯一方法。然而，一些虚拟化解决方案确实提供了良好的TSC同步机制。为了处理一些误报测试结果，VMware在Linux内核中创建了一个新的合成TSC_RELIABLE特性位来绕过TSC同步测试。其他内核组件也使用这个标志来绕过TSC同步测试。下面的命令可以用来检查这个新的合成CPU特性，
cat  /proc/cpuinfo | grep "tsc_reliable"

如果我们可以在CPU上设置特征位，我们应该能够信任这个平台上的TSC源。但请记住，TSC处理中的软件错误仍然可能导致问题。

3.1.2 SMP系统的TSC同步行为​

在UP系统中，CPU的TSC同步行为是由CPU的TSC能力决定的。而在SMP系统上，跨多个CPU插槽的TSC同步问题可能是一个大问题。SMP系统有三种类型，

  • 没有同步机制 在大多数较老的SMP和早期的多核机器上，TSC不能在处理器之间同步。因此，如果一个应用程序要在一个处理器上读取TSC，然后被操作系统移动到另一个处理器，然后再次读取TSC，那么可能会出现“时间倒流”。SMP机器上的“可变TSC”和“恒定TSC”cpu都有这个问题。
  • 同一主板上多个CPU插槽之间的同步 在CPU支持“不变TSC”后，最新的SMP系统可以确保TSC在多个CPU之间同步。在引导时，所有具有相同RESET信号的cpu都被重置，tsc以相同的速率增加。
  • 没有同步机制的跨多个机柜、刀片或主板 根据主板和计算机制造商的设计，不同主板上的不同cpu可能连接不同的时钟信号，这无法保证TSC同步。 例如，在SGI UV系统上，TSC不会在刀片之间同步。SGI提供的补丁试图在这种平台上禁用TSC时钟源。 即使CPU具有“不变TSC”特性，但SMP系统仍然不能提供可靠的TSC。由于这个原因，Linux内核必须依赖一些启动时间或运行时测试，而不是仅仅检测CPU能力。测试同步测试代码通过调用write_tsc代码来拥有TSC值修复代码。实际上，英特尔CPU提供了一个MSR寄存器，允许软件更改TSC值。这就是write_tsc的工作原理。然而，很难在多个CPU上发出每个CPU指令以使TSC获得同步值。因此，Linux内核只检查tsc同步，现在不会写入tsc。 如果在Linux内核引导过程中TSC同步测试通过，下面的sysfs文件将导出TSC作为当前时钟源。
$ cat /sys/devices/system/clocksource/clocksource0/current_clocksource
tsc

3.1.3 非intel平台​

非intel x86平台有不同的故事。当前Linux内核将所有非intel SMP系统视为非同步TSC系统。请参阅tsc.c中的unsynchronized_tsc代码。LKML也有AMD 文档。

3.1.4 CPU hotplug​

CPU热插拔将引入一个新的CPU，它可能没有比现有CPU同步的TSC值。理论上，系统软件、BIOS或SMM代码都可以为CPU热插拔进行TSC同步。 在Linux内核CPU热插拔代码路径中，它将检查tsc同步，并可能通过调用mark_tsc_unstable来禁用tsc时钟源。Linux内核使用write_tsc调用实现TSC同步算法。但是最近的Linux代码已经删除了由于同步代码的实现，因为没有可靠的软件机制来确保TSC值完全相同，即在完全相同的时间向多个cpu发出多条指令。 因此，根据我的理解，Linux TSC同步CPU热插拔场景取决于硬件/固件行为。

3.1.5 其他固件问题​

由于TSC值是可写的，固件代码可能会改变TSC值，从而导致操作系统中的TSC同步问题。 有一个LKML讨论提到一些BIOS SMI处理程序试图通过更改TSC值来隐藏其执行。 另一个例子是电源管理处理中的相关固件行为。如前所述，具有“不变TSC”特性的CPU可以避免在CPU深c状态变化期间TSC速率的变化。然而，一些x86固件实现在其TSC同步实现中改变了TSC值。在这种情况下，TSC同步从固件工作，但从软件的角度可能会中断。Linux内核必须创建一个补丁来处理ACPI挂起/恢复，以确保TSC同步在操作系统中仍然有效。

3.1.6 其他硬件问题​

TSC同步功能高度依赖于电路板制造商的设计。例如，时钟源可靠性问题。我曾经遇到过由于时钟源不可靠导致的硬件错误。由于错误，Linux内核TSC同步测试代码(tsc_sync.c中的check_tsc_sync_source)报告错误消息并禁用TSC作为时钟源。 另一个LKML讨论也提到SMP时钟信号中TSC漂移是由于温度问题。这最终可能导致Linux检测到TSC包装问题。

3.1.7 总结​

TSC同步功能不容易得到x86平台供应商的支持。在Linux下，我们可以使用以下两个步骤来检查平台功能:

  • 检查CPU能力标志 例如Linux下的/proc/cpuinfo，或者使用cpuid指令。请参考3.1.1节。请注意，VMware虚拟机有一个特殊的标志。

  • 检查现在内核的时钟源 请参考3.1.2章节 依赖TSC同步的用户应用程序可以执行上述两步检查，以确认TSC是否可靠。然而，根据TSC问题的根本原因，内核可能无法测试出所有不可靠的情况。例如，TSC时钟仍然有可能在运行时出现问题。在这种情况下，Linux可能会动态地从tsc时钟源切换到其他时钟源。

    3.2 在TSC使用过程中的软件bugs​

    3.2.1 TSC计算溢出问题​

    rdtsc的直接返回值是CPU周期，但延迟或时间需要一个规则的时间单位:ns或us。 理论上，64位TSC寄存器足以节省CPU周期，根据Intel 64 Architecture SDM Vol. 3A 2-33，

时间戳计数器是一个特定于模型的64位计数器，每次处理器复位时将其重置为零。
如果不复位，当处理器以3GHz时钟速率工作时，计数器每年将增加~9.5 x 1016倍。
在这个时钟频率下，计数器绕一圈需要190多年。

这里的溢出问题是在cycle_2_ns或cycle_2_us的实现中，它们需要将cycle与另一个大数相乘，那么这可能会导致溢出问题。 根据当前的Linux实现，以下情况溢出错误可能发生，

  • Linux操作系统已运行超过208天
  • Linux操作系统重启后，由于keexec特性，不会导致TSC复位
  • 一些可能的硬件/固件错误导致在Linux操作系统重启期间没有TSC复位 Linux内核在尝试使用TSC获取调度器时钟时，经常会遇到溢出错误(v3.2内核补丁 v3.4内核补丁 )。 为了避免溢出错误，Linux内核中的cycle_2_ns变得比我们之前提到的更复杂。
 * ns = cycles * cyc2ns_scale / SC
 *
 * Although we may still have enough bits to store the value of ns,
 * in some cases, we may not have enough bits to store cycles * cyc2ns_scale,
 * leading to an incorrect result.
 *
 * To avoid this, we can decompose 'cycles' into quotient and remainder
 * of division by SC.  Then,
 *
 * ns = (quot * SC + rem) * cyc2ns_scale / SC
 *    = quot * cyc2ns_scale + (rem * cyc2ns_scale) / SC
 *            - sqazi@google.com

与Linux内核不同，一些用户应用程序使用下面的公式，如果TSC周期超过2小时，可能会导致溢出!

ns = cycles * 10^6 / cpu_khz

3.2.2 不正确的CPU使用频率​

Linux内核在实现中使用CPU KHZ而不是GHZ/MHZ。请阅读之前关于cycle_2_ns实现的部分。这里使用KHZ的主要原因是:精度更高。旧的内核代码以前使用MHZ，这个补丁修复了这个问题。

3.2.3 乱序执行问题​

如果要度量的代码非常小，那么上面的rdtsc函数可能需要由LFENCE或RDTSCP重新实现。否则，这将引入CPU乱序执行引起的精度问题。 参见Intel 64 Architecture SDM Vol. 2B中的描述。

The RDTSC instruction is not a serializing instruction. It does not necessarily wait until 
all previous instructions have been executed before reading the counter.
Similarly, subsequent instructions may begin execution before the read operation is performed.
If software requires RDTSC to be executed only after all previous instructions have completed locally,
it can either use RDTSCP (if the processor supports that instruction) or execute the sequence LFENCE;RDTSC.
RDTSC指令不是序列化指令。在读取计数器之前，它不必等待所有先前的指令执行完毕。
类似地，后续指令可以在执行读操作之前开始执行。如果软件要求只有在所有先前的指令在本地完成之后才执行RDTSC，
那么它可以使用RDTSCP(如果处理器支持该指令)或执行序列LFENCE;RDTSC。

Linux内核中有一个示例来实现rdtsc_ordered 有关正确的乱序实现，请参阅英特尔白皮书:如何在英特尔®IA-32和IA-64指令集架构上对代码执行时间进行基准测试

3.3 跨不同虚拟化程序的TSC模拟​

虚拟化技术给客户操作系统的时间管理带来了很多挑战。本节只讨论以下情况:主机可以检测到TSC时钟源，客户机软件可能对TSC敏感，当任务在vCPU上运行时，试图发出rdtsc指令访问TSC寄存器。 与物理问题相比，虚拟化给TSC同步带来了更多的挑战。例如，如果源主机和目标主机的硬件和软件级别不同，则虚拟机热迁移可能会导致TSC同步问题。

  • 平台类型差异(Intel vs AMD，可靠vs不可靠)

  • CPU主频(TSC增幅)

  • CPU启动时间(TSC初始值)

  • 虚拟化环境版本差异 因此，TSC同步在不同虚拟化程序上的行为可能导致TSC同步问题。

    3.3.1 基本的方法​

    根据管理程序的不同，可以使用以下方法处理rdtsc指令和TSC同步: （1）Native or pass-through-快速但可能不正确 管理程序不进行模拟。该指令直接在物理cpu上执行。这种模式有更快的性能，但可能会导致TSC对客户操作系统中的TSC敏感应用程序的TSC同步问题。 特别是，VM可以实时迁移到不同的机器上。保证TSC值在不同机器间同步是不可能的，也是不合理的。 （2）Emulated or Trap-正确，但缓慢

  • 完全虚拟化 Hypervisor将模拟TSC，然后rdtsc不直接在物理cpu上执行。这种模式会导致rdtsc指令的性能下降，但对TSC敏感的应用程序提供了可靠性。Intel和AMD cpu支持VMX和SVM，这允许硬件加速的rdtsc仿真。

  • 半虚拟化 为了优化rdtsc性能，一些管理程序提供了PVRDTSCP，允许对VM中的软件进行半虚拟化(修改)以获得更好的性能。如果VM中的用户应用程序直接发出rdtsc指令，则半虚拟化解决方案无法工作。 （3）Hybrid（混合型）——正确但可能缓慢 一种混合算法，确保以下因素的正确性:

  • 正确性要求

  • 硬件TSC功能

  • 一些特殊的虚拟机使用场景:保存/恢复/迁移虚拟机 当本机运行可以获得良好的性能和正确性时，将不进行仿真而直接本机运行。如果虚拟机管理程序不能使用本机方式，它将使用全虚拟化或准虚拟化技术来确保正确性。

    3.3.2 不同管理程序上的实现​

    下面是关于各种管理程序上的TSC支持的详细信息， （1）VMware ESX 4.X和3.x不会在vcpu之间进行TSC同步。但是从esx5开始，管理程序始终保持TSC在vcpu之间同步。VMware使用混合算法来确保TSC同步，即使底层硬件不支持TSC同步。对于具有良好TSC同步支持的硬件，rdtsc仿真可以获得良好的性能。但是当硬件不能提供TSC同步支持时，TSC仿真将会变慢。 然而，VMware TSC仿真不能确保cpu之间没有边际TSC倾斜。因此，Linux启动TSC同步检查可能会失败。 出于这个原因，在Linux guest中，VMware创建了一个新的综合TSC_RELIABLE特性位来绕过Linux TSC同步测试。Linux [VMware cpu detect code] gives the good comments about TSC sync testing issues,

     /*
      * VMware hypervisor takes care of exporting a reliable TSC to the guest.
      * Still, due to timing difference when running on virtual cpus, the TSC can
      * be marked as unstable in some cases. For example, the TSC sync check at
      * bootup can fail due to a marginal offset between vcpus TSCs (though the
      * TSCs do not drift from each other).  Also, the ACPI PM timer clocksource
      * is not suitable as a watchdog when running on a hypervisor because the
      * kernel may miss a wrap of the counter if the vcpu is descheduled for a
      * long time. To skip these checks at runtime we set these capability bits,
      * so that the kernel could just trust the hypervisor with providing a
      * reliable virtual TSC that is suitable for timekeeping.
      */
     static void vmware_set_cpu_features(struct cpuinfo_x86 *c)
     {
         set_cpu_cap(c, X86_FEATURE_CONSTANT_TSC);
         set_cpu_cap(c, X86_FEATURE_TSC_RELIABLE);
     }

Linux 2.6.29版本进行了补丁合并。

VMware还在VMware虚拟机中提供计时功能，以讨论TSC仿真问题。详细信息请参考本文档。

（2）Hyper-V Hyper-V不提供TSC仿真。因此，hyper-V上的TSC是不可靠的。但问题是，hyper-V Linux CPU驱动程序从来没有报告过这个问题，这意味着TSC时钟源仍然可以使用，如果它碰巧通过了Linux内核TSC同步测试。就在20天前，Linux内核4.3-rc1补丁在Hyper-V Linux客户机上禁用了TSC时钟源。 （3）KVM 在最新的Linux guest操作系统中，KVM默认使用kvmclock驱动。

  • 尽可能实现完美的同步
  • 使用TSC稳定技术
  • 无频率补偿
  • 没有TSC捕获，用户空间rdtsc是不完善的
  • 映射pvclock并从 gettimeofday()通过VDSO/ vsycalls的方式调用kvmclock kvmclock的缺点是用户空间TSC读取仍然会有问题。因为用户空间rdtsc不能通过kvmclock修复，修复它的唯一方法是TSC emulation/trap.。 对于带有kvmclock驱动程序的传统操作系统，KVM客户机似乎在本机运行真实的rdtsc。 但是，我在这里没有看到KVM代码支持TSC陷阱。刚刚找到了一个旧的内核补丁来支持TSC陷阱。但是我没有发现它被合并到Linux主线中。 由于上述原因，我认为在KVM Linux客户机上运行对rdtsc敏感的应用程序是有问题的。KVM实际上有一个关于计时的内核文档，但是文档中没有足够的关于KVM实现的信息。

（4）Xen 在Xen 4.0之前，它只支持本机模式。Xen 4.0提供了tsc_mode参数，允许管理员根据需求在4种模式之间切换。默认情况下，Xen 4.0使用混合模式。这个Xen文档非常详细地讨论了TSC emulation。

3.3.3 总结​

VMware和Xen似乎提供了TSC同步的最佳解决方案。KVM PV emulation从不解决用户空间rdtsc用例问题。而且hyper-V没有TSC同步解决方案。所有这些TSC同步解决方案都提供了让Linux内核TSC时钟源持续工作的方法。尽管某些管理程序支持TSC同步，但在VM中仍然可以观察到微小的TSC偏差。因此，应用程序可能仍然有错误的TSC持续时间用于时间测量。

四、结论

Linux内核可以检测到TSC同步问题，并尝试“TSC-resilient”。主要问题在于用户应用。对于用户应用程序，特别是在虚拟化环境下，没有可靠的TSC同步机制。以下是建议: （1）如果可能的话，避免在用户应用程序中使用rdtsc。 并不是所有的硬件、管理程序都是TSC安全的，这意味着TSC的行为可能不正确。 TSC的使用将导致跨各种x86平台或不同管理程序的软件移植错误。利用系统调用或vsycall将使软件具有可移植性，特别是对于虚拟化环境。 （2）如果您必须使用它，请使您的应用程序“TSC-resilient”。 在调试中使用它，但不要在功能区中使用rdtsc。 正如我们上面提到的，直到今天，Linux内核也很难处理它。如果可能的话，先学习Linux代码。性能测量和调试工具可能只是可用的案例，但是要准备好处理各种案例和软件移植问题。 了解来自硬件、操作系统内核、管理程序的风险。编写一个“TSC-resilient”应用程序，以确保您的应用程序在TSC值错误时仍然可以正常运行。
